## 保留的核心判断

1. FreeCut 是主界面和主项目。
2. HyperFrames 提供 HTML 视频组合、AI 技能、工作室、播放器和生产渲染。
3. 集成必须最小侵入、渐进增强、可回滚。
4. 用户应能在时间线上继续编辑 AI 生成结果。
5. 渲染应支持 FreeCut 原生导出、HyperFrames 生产器和混合叠加。
6. 发布必须有测试、文档、支持和性能门禁。

## 被修正的旧设计

### 独立时间线类型

旧设计提出新增 `hyperframes-composition`。新方案不采用。原因：

- 当前 FreeCut 已有 `composition` 类型。
- 复用组合片段可以继承时间线行为。
- 通过 `sourceKind: 'hyperframes'` 即可区分来源。
- 当前代码已经按该方向落地。

### 时间线项内嵌完整 HTML

旧设计把 HTML 放入时间线项。新方案不采用。原因：

- 不利于多文件组合。
- 不利于资产管理。
- 不利于工作室编辑。
- 不利于源目录导出和重新渲染。
- 不利于安全校验和版本追溯。

新方案使用 HyperFrames 项目目录作为权威源。

### 命令行即产品能力

旧文档多处把技能或命令行调用写成主要入口。新方案改为：

- 命令行可以作为本地服务执行器。
- 用户界面必须是 FreeCut 主界面。
- 技能必须包装成生成面板、推荐、计划、队列、预览、确认和导入。

### 固定模型假设

旧文档提到部分模型或供应商，但没有完整模型治理。新方案补齐：

- 任意供应商。
- 私有网关。
- 本地模型。
- 能力绑定。
- 凭据引用。
- 成本预算。
- 权限策略。
- 失败回退。

### 任意脚本直接预览

旧方案对 HTML 安全边界描述不足。新方案明确：

- 主预览默认沙箱。
- 导入前校验。
- 阻塞诊断禁止导入和导出。
- 开发模式与标准模式分离。

## 后续使用方式

后续写实现计划时，应以本目录为主规格，旧文档只作为背景资料。若旧文档与本目录冲突，采用本目录方案，尤其是以下不可逆转决策：

- 复用 `composition` 时间线类型。
- 使用清单式 HyperFrames 项目目录。
- 主界面内完成生成、编辑和导出。
- 模型配置中心支持任意模型。
- AI 写入必须预览、确认、记录来源和支持回滚。
